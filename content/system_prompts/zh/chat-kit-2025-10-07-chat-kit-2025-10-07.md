import { TabItem, Tabs } from "@astrojs/starlight/components";

客户端工具让你的后端代理将工作委托给浏览器。当代理调用客户端工具时，ChatKit 会暂停响应，直到你的 UI 解析 `onClientTool`。

使用此选项来访问仅存在于浏览器中的 API（本地存储、UI 状态、硬件令牌等），或当客户端视图需要与服务端更改同步更新时使用。完成后，向服务器返回一个可 JSON 序列化的负载。

## 生命周期概览

1. 在后端代理和 ChatKit 中配置相同的客户端工具名称。
2. ChatKit 收到来自代理的工具调用，并调用 `onClientTool({ name, params })`。
3. 你的处理程序在浏览器中运行，并返回一个描述结果的对象（或 `Promise`）。ChatKit 将该负载转发给你的后端。
4. 如果处理程序抛出异常，工具调用失败，助手会收到错误消息。

## 在你的 UI 中注册处理程序

<Tabs syncKey="client-tools-target">
  <TabItem label="React">
  import { ChatKit, useChatKit } from '@openai/chatkit-react';
  import type { ChatKitOptions } from '@openai/chatkit';

  type ClientToolCall =
    | { name: 'send_email'; params: { email_id: string } }
    | { name: 'open_tab'; params: { url: string } };

  export function SupportInbox({ clientToken }: { clientToken: string }) {
    const { control } = useChatKit({
      api: { clientToken },
      onClientTool: async (toolCall) => {
        const { name, params } = toolCall as ClientToolCall;

        switch (name) {
          case 'send_email':
            const result = await sendEmail(params.email_id);
            return { success: result.ok, id: result.id };
          case 'open_tab':
            window.open(params.url, '_blank', 'noopener');
            return { opened: true };
          default:
            throw new Error(`Unhandled client tool: ${name}`);
        }
      },
    } satisfies ChatKitOptions);

    return <ChatKit control={control} className="h-[600px] w-[320px]" />;
  }
  </TabItem> <TabItem label="Vanilla JS">
  const chatkit = document.getElementById('chatkit');

  chatkit.setOptions({
    api: { clientToken },
    async onClientTool({ name, params }) {
      if (name === 'get_geolocation') {
        const position = await new Promise<GeolocationPosition>((resolve, reject) => {
          navigator.geolocation.getCurrentPosition(resolve, reject);
        });
        return {
          latitude: position.coords.latitude,
          longitude: position.coords.longitude,
        };
      }

      throw new Error(`Unknown client tool: ${name}`);
    },
  });
  </TabItem>
</Tabs>

- 如果工具不需要返回数据，返回 {} 以将调用标记为成功。

概览

ChatKit 是一个用于构建高质量、AI 驱动的聊天体验的框架。它专为希望快速为其应用添加高级对话智能的开发者而设计——设置最少，无需重复造轮子。ChatKit 开箱即提供完整、可用于生产的聊天界面。

主要功能

- 深度 UI 自定义，使 ChatKit 感觉像是你应用的一等公民
- 内置响应流式传输，实现交互式、自然的对话
- 工具和工作流集成，用于可视化代理操作和思维链推理
- 直接在聊天中渲染的丰富交互式小组件
- 附件处理，支持文件和图像上传
- 线程和消息管理，用于组织复杂对话
- 源注释和实体标记，用于透明度和引用
- 只需将 ChatKit 组件放入你的应用，配置几个选项，就可以开始了。

## ChatKit 有何不同？

ChatKit 是一个框架无关的即插即用聊天解决方案。
你无需构建自定义 UI、管理底层聊天状态，或自己拼凑各种功能。
只需添加 ChatKit 组件，给它一个客户端令牌，并根据需要自定义聊天体验，无需额外工作。

## 服务器集成（Python SDK 示例）

ChatKit 的服务器集成提供了一种灵活且框架无关的方法来构建实时聊天体验。通过实现 `ChatKitServer` 基类及其 `respond` 方法，你可以配置你的工作流如何响应用户输入，从使用工具到返回丰富的显示小组件。ChatKit 服务器集成暴露单个端点，并支持 JSON 和服务器发送事件（SSE）来流式传输实时更新。

### 安装

使用以下命令安装 `openai-chatkit` 包：

pip install openai-chatkit

定义服务器类
ChatKitServer 基类是 ChatKit 服务器实现的主要构建块。
每次用户发送消息时都会执行 respond 方法。它负责通过流式传输一组事件来提供答案。respond 方法可以返回助手消息、工具状态消息、工作流、任务和小组件。
ChatKit 还提供使用 Agents SDK 实现 respond 的辅助工具。主要的是 stream_agent_response，它将流式传输的 Agents SDK 运行转换为 ChatKit 事件。
如果你在输入框中启用了模型或工具选项，它们将出现在 respond 中的 input_user_message.inference_options 下。你的集成负责在执行推理时处理这些值。
示例服务器实现，调用 Agent SDK runner 并将结果流式传输到 ChatKit UI：
class MyChatKitServer(ChatKitServer):
    def __init__(
        self, data_store: Store, attachment_store: AttachmentStore | None = None
    ):
        super().__init__(data_store, attachment_store)

    assistant_agent = Agent[AgentContext](
        model="gpt-4.1",
        name="Assistant",
        instructions="You are a helpful assistant"
    )

    async def respond(
        self,
        thread: ThreadMetadata,
        input: UserMessageItem | None,
        context: Any,
    ) -> AsyncIterator[ThreadStreamEvent]:
        context = AgentContext(
            thread=thread,
            store=self.store,
            request_context=context,
        )
        result = Runner.run_streamed(
            self.assistant_agent,
            await simple_to_agent_input(input) if input else [],
            context=context,
        )
        async for event in stream_agent_response(
            context,
            result,
        ):
            yield event
## 设置端点

ChatKit 与服务器无关。所有通信都通过单个 POST 端点进行，该端点直接返回 JSON 或流式传输 SSE JSON 事件。

你负责使用你选择的 Web 服务器框架定义端点。

使用 ChatKit 与 FastAPI 的示例：

app = FastAPI()
data_store = PostgresStore()
attachment_store = BlobStorageStore(data_store)
server = MyChatKitServer(data_store, attachment_store)

@app.post("/chatkit")
async def chatkit_endpoint(request: Request):
    result = await server.process(await request.body(), {})
    if isinstance(result, StreamingResult):
        return StreamingResponse(result, media_type="text/event-stream")
    else:
        return Response(content=result.json, media_type="application/json")

数据存储

ChatKit 需要存储关于线程、消息和附件的信息。上面的示例使用了一个提供的仅用于开发的 SQLite 数据存储实现（SQLiteStore）。
你负责使用你选择的数据存储实现 chatkit.store.Store 类。在实现存储时，你必须允许 Thread/Attachment/ThreadItem 类型形态在库版本之间发生变化。对于关系数据库，推荐的方法是将模型序列化为 JSON 类型的列，而不是将模型字段分散到多个列中。

class Store(ABC, Generic[TContext]):
    def generate_thread_id(self, context: TContext) -> str: ...

    def generate_item_id(
        self,
        item_type: Literal["message", "tool_call", "task", "workflow", "attachment"],
        thread: ThreadMetadata,
        context: TContext,
    ) -> str: ...

    async def load_thread(self, thread_id: str, context: TContext) -> ThreadMetadata: ...

    async def save_thread(self, thread: ThreadMetadata, context: TContext) -> None: ...

    async def load_thread_items(
        self,
        thread_id: str,
        after: str | None,
        limit: int,
        order: str,
        context: TContext,
    ) -> Page[ThreadItem]: ...

    async def save_attachment(self, attachment: Attachment, context: TContext) -> None: ...

    async def load_attachment(self, attachment_id: str, context: TContext) -> Attachment: ...

    async def delete_attachment(self, attachment_id: str, context: TContext) -> None: ...

    async def load_threads(
        self,
        limit: int,
        after: str | None,
        order: str,
        context: TContext,
    ) -> Page[ThreadMetadata]: ...

    async def add_thread_item(
        self, thread_id: str, item: ThreadItem, context: TContext
    ) -> None: ...

    async def save_item(self, thread_id: str, item: ThreadItem, context: TContext) -> None: ...

    async def load_item(self, thread_id: str, item_id: str, context: TContext) -> ThreadItem: ...

    async def delete_thread(self, thread_id: str, context: TContext) -> None: ...

默认实现使用 UUID4 字符串为标识符添加前缀（例如 msg_4f62d6a7f2c34bd084f57cfb3df9f6bd）。如果你的集成需要确定性或预分配的标识符，请覆盖 generate_thread_id 和/或 generate_item_id；每当 ChatKit 需要创建新线程 id 或新线程项 id 时，都会使用它们。

附件存储

用户可以上传附件（文件和图像）以包含在聊天消息中。你负责提供存储实现并处理上传。ChatKitServer 的 attachment_store 参数应实现 AttachmentStore 接口。如果未提供，对附件的操作将引发错误。
ChatKit 支持直接上传和两阶段上传，可通过 ChatKitOptions.composer.attachments.uploadStrategy 在客户端配置。

访问控制

附件元数据和文件字节不受 ChatKit 保护。每个 AttachmentStore 方法都会接收你的请求上下文，以便你可以在发放附件 ID、字节或签名 URL 之前强制执行线程级和用户级授权。当调用者不拥有该附件时拒绝访问，并生成快速过期的下载 URL。跳过这些检查可能会泄露客户数据。

### 直接上传

直接上传 URL 在客户端作为创建选项提供。

客户端将向该 URL POST 带有 `file` 字段的 `multipart/form-data`。服务器应：

1. 将附件元数据（`FileAttachment | ImageAttachment`）持久化到数据存储，并将文件字节持久化到你的存储。
2. 以 `FileAttachment | ImageAttachment` 的 JSON 表示形式响应。

### 两阶段上传

- **阶段 1（注册和上传 URL 配置）**：客户端调用 `attachments.create`。ChatKit 持久化一个 `FileAttachment | ImageAttachment`，设置 `upload_url` 并返回它。建议在 `upload_url` 中包含 `Attachment` 的 `id`，以便你可以将文件字节与该 `Attachment` 关联。
- **阶段 2（上传）**：客户端使用 `multipart/form-data` 字段 `file` 将字节 POST 到返回的 `upload_url`。

### 预览

要渲染附加到用户消息的图像缩略图，请将 `ImageAttachment.preview_url` 设置为可渲染的 URL。如果你需要过期 URL，请不要持久化该 URL；在将附件返回给客户端时按需生成它。

### AttachmentStore 接口

你通过提供 `AttachmentStore` 方法来实现存储细节：

class AttachmentStore(ABC, Generic[TContext]):
    async def delete_attachment(self, attachment_id: str, context: TContext) -> None: ...
    async def create_attachment(self, input: AttachmentCreateParams, context: TContext) -> Attachment: ...
    def generate_attachment_id(self, mime_type: str, context: TContext) -> str: ...

注意：存储不必自己持久化字节。它可以充当代理，为上传和预览签发签名 URL（例如 S3/GCS/Azure），而你的单独上传端点写入对象存储。

将文件附加到 Agent SDK 输入

你还负责决定如何将附件附加到 Agent SDK 输入。你可以将文件存储在你自己的存储中，并将它们作为 base64 编码的负载附加，或将它们上传到 OpenAI Files API 并向 Agent SDK 提供文件 ID。

    """Replace with your blob-store fetch (S3, local disk, etc.)."""
    ...

class MyConverter(ThreadItemConverter):
    async def attachment_to_message_content(
        self, input: Attachment
    ) -> ResponseInputContentParam:
        content = await read_attachment_bytes(input.id)
        data = (
            "data:"
            + str(input.mime_type)
            + ";base64,"
            + base64.b64encode(content).decode("utf-8")

                detail="auto",
                image_url=data,

        # Note: Agents SDK currently only supports pdf files as ResponseInputFileParam.
        # To send other text file types, either convert them to pdf on the fly or

        return ResponseInputFileParam(
            type="input_file",
            file_data=data,
            filename=input.name or "unknown",
        )

## 客户端工具用法

ChatKit 服务器实现可以触发客户端工具。

该工具必须在客户端初始化 ChatKit 时以及在服务器上设置 Agents SDK 时都注册。

要从 Agents SDK 触发客户端工具，请在工具实现中设置 `ctx.context.client_tool_call`，包含客户端工具名称和参数。客户端工具执行的结果将提供回模型。

**注意：** 代理行为必须设置为 `tool_use_behavior=StopAtTools`，并将所有客户端工具包含在 `stop_at_tool_names` 中。这会使代理停止生成新消息，直到客户端工具调用被 ChatKit UI 确认。

**注意：** 每轮只能触发一个客户端工具调用。

**注意：** 客户端工具是由代理在服务端推理期间调用的客户端回调。如果你对由用户与小组件交互触发的客户端回调感兴趣，请参阅[客户端操作](actions.md/#client)。

@function_tool(description_override="Add an item to the user's todo list.")
async def add_to_todo_list(ctx: RunContextWrapper[AgentContext], item: str) -> None:
    ctx.context.client_tool_call = ClientToolCall(
        name="add_to_todo_list",
        arguments={"item": item},
    )

assistant_agent = Agent[AgentContext](
    model="gpt-4.1",
    name="Assistant",
    instructions="You are a helpful assistant",
    tools=[add_to_todo_list],
    tool_use_behavior=StopAtTools(stop_at_tool_names=[add_to_todo_list.name]),
)

Agents SDK 集成

ChatKit 服务器独立于 Agents SDK。只要从 respond 方法返回正确的事件，ChatKit UI 就会按预期显示对话。
ChatKit 库提供与 Agents SDK 集成的辅助工具：

- AgentContext - 调用 Agents SDK 时应使用的上下文类型。它提供了一些辅助方法，用于从工具调用中流式传输事件、渲染 widget，以及发起客户端工具调用。
- stream_agent_response - 一个辅助函数，用于将流式运行的 Agents SDK 转换为 ChatKit 事件。
- ThreadItemConverter - 一个辅助类，你很可能需要扩展它，以将 ChatKit 线程项转换为 Agents SDK 输入项。
- simple_to_agent_input - 一个辅助函数，使用默认的线程项转换。默认转换能力有限，但有助于快速上手。

async def respond([]

## Widgets

Widget 是可以在聊天中显示的富 UI 组件。你可以直接从 `respond` 方法返回 widget（如果你希望无条件这样做），也可以从由模型触发的工具调用中返回。

直接从 `respond` 方法返回 widget 的示例：

async def respond(
        self,
        thread: ThreadMetadata,
        input: UserMessageItem | None,
        context: Any,
    ) -> AsyncIterator[ThreadStreamEvent]:
    widget = Text(
        id="description",
        value="Text widget",
    )

    async for event in stream_widget(
        thread,
        widget,
        generate_id=lambda item_type: self.store.generate_item_id(
            item_type, thread, context
        ),
    ):
        yield event

从工具调用返回 widget 的示例：
@function_tool(description_override="Display a sample widget to the user.")
async def sample_widget(ctx: RunContextWrapper[AgentContext]) -> None:
    widget = Text(
        id="description",
        value="Text widget",
    )

    await ctx.context.stream_widget(widget)

上面的示例返回一个完全完成的静态 widget。你也可以通过从生成器函数中产出 widget 的新版本来流式传输一个不断更新的 widget。ChatKit 框架会为 widget 中已更改的部分发送更新。
注意：目前，只有标记了 id 的 <Text> 和 <Markdown> 组件会流式传输其文本更新。
async def sample_widget(ctx: RunContextWrapper[AgentContext]) -> None:
     description_text = Runner.run_streamed(
        email_generator, "ChatKit is the best thing ever"
    )

    async def widget_generator() -> AsyncGenerator[Widget, None]:
        text_widget_updates = accumulate_text(
            description_text.stream_events(),
            Text(
                id="description",
                value="",
                streaming=True
            ),
        )

        async for text_widget in text_widget_updates:
            yield Card(
                children=[text_widget]
            )

    await ctx.context.stream_widget(widget_generator())

在上面的示例中，accumulate_text 函数用于将 Agents SDK 运行的结果流式传输到 Text widget 中。
定义 widget
你可能会发现用 JSON 编写 widget 更容易。你可以将 JSON widget 解析为 WidgetRoot 实例，供你的服务器进行流式传输：

## 线程元数据

ChatKit 提供了一种方式来存储与线程关联的任意信息。这些信息不会发送到 UI。

元数据的一个用例是保留 [`previous_response_id`](https://platform.openai.com/docs/api-reference/responses/create#responses-create-previous_response_id)，从而避免为一次 Agent SDK 运行重新发送所有项。

previous_response_id = thread.metadata.get("previous_response_id")

# Run the Agent SDK run with the previous response id
result = Runner.run_streamed(
    agent,
    input=...,
    previous_response_id=previous_response_id,
)

# Save the previous response id for the next run
thread.metadata["previous_response_id"] = result.response_id

# ChatKit 操作

操作是 ChatKit SDK 前端在用户未提交消息的情况下触发流式响应的一种方式。它们也可用于触发 ChatKit SDK 之外的副作用。

## 触发操作

### 响应用户与 widget 的交互

可以通过将 `ActionConfig` 附加到任何支持它的 widget 节点来触发操作。例如，你可以响应 Button 上的点击事件。当用户点击此按钮时，操作将被发送到你的服务器，你可以在那里更新 widget、运行推理、流式传输新的线程项等。

Button(
    label="Example",
    onClickAction=ActionConfig(
      type="example",
      payload={"id": 123},
    )
)

操作也可以由你的前端通过 sendAction() 以命令式方式发送。当你需要 ChatKit 响应发生在 ChatKit 之外的交互时，这可能是最有用的，但它也可以用于在你需要同时在客户端和服务器端响应时串联操作（详见下文）。

await chatKit.sendAction({
  type: "example",
  payload: { id: 123 },
});

处理操作

在服务器端

默认情况下，操作会被发送到你的服务器。你可以通过在 ChatKitServer 上实现 action 方法来在服务器端处理操作。

### 客户端

有时你会希望在客户端集成中处理操作。为此，你需要通过在 `ActionConfig` 中添加 `handler="client"` 来指定该操作应发送到你的客户端操作处理器。

Button(
    label="Example",
    onClickAction=ActionConfig(
      type="example",
      payload={"id": 123},
      handler="client"
    )
)

然后，当操作被触发时，它将被传递给你在实例化 ChatKit 时提供的回调。

async function handleWidgetAction(action: {type: string, Record<string, unknown>}) {
  if (action.type === "example") {
    const res = await doSomething(action)

    // You can fire off actions to your server from here as well.
    // e.g. if you want to stream new thread items or update a widget.
    await chatKit.sendAction({
      type: "example_complete",
      payload: res
    })
  }
}

chatKit.setOptions({
  // other options...
  widgets: { onAction: handleWidgetAction }
})

强类型操作

默认情况下，Action 和 ActionConfig 不是强类型的。不过，我们在 Action 上提供了一个 create 辅助方法，使得从一组强类型操作生成 ActionConfig 变得很容易。

class ExamplePayload(BaseModel)
    id: int

ExampleAction = Action[Literal["example"], ExamplePayload]
OtherAction = Action[Literal["other"], None]

AppAction = Annotated[
  ExampleAction
  | OtherAction,
  Field(discriminator="type"),
]

ActionAdapter: TypeAdapter[AppAction] = TypeAdapter(AppAction)

def parse_app_action(action: Action[str, Any]): AppAction

# 编排多个 agent

编排指的是 agent 在你的应用中的流转。哪些 agent 运行、以什么顺序运行，以及它们如何决定接下来发生什么？编排 agent 主要有两种方式：

1. 让 LLM 做出决策：这利用 LLM 的智能来规划、推理，并据此决定采取哪些步骤。
2. 通过代码编排：通过你的代码确定 agent 的流转。

你可以混合搭配这些模式。每种模式都有自己的权衡，如下所述。

## 通过 LLM 编排

agent 是一个配备了指令、工具和交接的 LLM。这意味着，给定一个开放式任务，LLM 可以自主规划如何完成该任务，使用工具采取行动并获取数据，并使用交接将任务委派给子 agent。例如，一个研究 agent 可以配备如下工具：

- 网络搜索，以在线查找信息
- 文件搜索和检索，以搜索专有数据和连接
- 计算机使用，以在计算机上采取行动
- 代码执行，以进行数据分析
- 交接给擅长规划、报告撰写等的专业 agent。

当任务是开放式的，并且你希望依赖 LLM 的智能时，这种模式非常合适。这里最重要的策略是：

1. 投入精力编写好的提示词。明确说明有哪些工具可用、如何使用它们，以及它必须在什么参数范围内运行。
2. 监控你的应用并迭代。查看哪里出了问题，并迭代你的提示词。
3. 允许 agent 进行内省和改进。例如，在循环中运行它，让它自我批评；或者，提供错误消息并让它改进。
4. 拥有擅长单一任务的专业 agent，而不是拥有一个被期望样样精通的通用 agent。
5. 投入 [evals](https://platform.openai.com/docs/guides/evals)。这让你可以训练你的 agent 改进并更好地完成任务。

## 通过代码编排

虽然通过 LLM 编排很强大，但通过代码编排在速度、成本和性能方面使任务更加确定和可预测。这里的常见模式是：

- 使用[结构化输出](https://platform.openai.com/docs/guides/structured-outputs)生成格式良好的数据，你可以用代码检查这些数据。例如，你可以要求 agent 将任务分类为几个类别，然后根据类别选择下一个 agent。
- 通过将一个 agent 的输出转换为下一个 agent 的输入来串联多个 agent。你可以将撰写博客文章这样的任务分解为一系列步骤——进行研究、撰写大纲、撰写博客文章、批评它，然后改进它。
- 在 `while` 循环中运行执行任务的 agent，并搭配一个评估并提供反馈的 agent，直到评估者表示输出通过某些标准。
- 并行运行多个 agent，例如通过 `asyncio.gather` 等 Python 原语。当你拥有多个互不依赖的任务时，这对于提高速度很有用。

我们在 [`examples/agent_patterns`](https://github.com/openai/openai-agents-python/tree/main/examples/agent_patterns) 中有许多示例。

# 结果

当你调用 `Runner.run` 方法时，你会得到以下之一：

- 如果你调用 `run` 或 `run_sync`，则得到 [`RunResult`][agents.result.RunResult]
- 如果你调用 `run_streamed`，则得到 [`RunResultStreaming`][agents.result.RunResultStreaming]

这两者都继承自 [`RunResultBase`][agents.result.RunResultBase]，大多数有用的信息都在那里。

## 最终输出

[`final_output`][agents.result.RunResultBase.final_output] 属性包含最后运行的 agent 的最终输出。这要么是：

- 一个 `str`，如果最后一个 agent 没有定义 `output_type`
- 一个 `last_agent.output_type` 类型的对象，如果该 agent 定义了输出类型。

!!! note

    `final_output` 的类型是 `Any`。由于交接的存在，我们无法对其进行静态类型标注。如果发生交接，这意味着任何 Agent 都可能是最后一个 agent，因此我们无法静态地知道可能的输出类型集合。

## 下一轮的输入

你可以使用 [`result.to_input_list()`][agents.result.RunResultBase.to_input_list] 将结果转换为一个输入列表，该列表将你提供的原始输入与 agent 运行期间生成的项连接起来。这使得将一个 agent 运行的输出传入另一次运行变得很方便，或者在循环中运行它并每次追加新的用户输入。

## 最后一个 agent

[`last_agent`][agents.result.RunResultBase.last_agent] 属性包含最后运行的 agent。根据你的应用，这通常对用户下次输入内容时很有用。例如，如果你有一个一线分诊 agent 交接给一个特定语言的 agent，你可以存储最后一个 agent，并在用户下次向该 agent 发送消息时重新使用它。

## 新项

[`new_items`][agents.result.RunResultBase.new_items] 属性包含运行期间生成的新项。这些项是 [`RunItem`][agents.items.RunItem]。一个运行项包装了 LLM 生成的原始项。

- [`MessageOutputItem`][agents.items.MessageOutputItem] 表示来自 LLM 的消息。原始项是生成的消息。
- [`HandoffCallItem`][agents.items.HandoffCallItem] 表示 LLM 调用了交接工具。原始项是来自 LLM 的工具调用项。
- [`HandoffOutputItem`][agents.items.HandoffOutputItem] 表示发生了交接。原始项是对交接工具调用的工具响应。你还可以从该项访问源/目标 agent。
- [`ToolCallItem`][agents.items.ToolCallItem] 表示 LLM 调用了某个工具。
- [`ToolCallOutputItem`][agents.items.ToolCallOutputItem] 表示某个工具被调用。原始项是工具响应。你还可以从该项访问工具输出。
- [`ReasoningItem`][agents.items.ReasoningItem] 表示来自 LLM 的推理项。原始项是生成的推理。

## 其他信息

### 护栏结果

[`input_guardrail_results`][agents.result.RunResultBase.input_guardrail_results] 和 [`output_guardrail_results`][agents.result.RunResultBase.output_guardrail_results] 属性包含护栏的结果（如果有）。护栏结果有时可能包含你想记录或存储的有用信息，因此我们将其提供给你。

### 原始响应

[`raw_responses`][agents.result.RunResultBase.raw_responses] 属性包含 LLM 生成的 [`ModelResponse`][agents.items.ModelResponse]。

### 原始输入

[`input`][agents.result.RunResultBase.input] 属性包含你提供给 `run` 方法的原始输入。在大多数情况下你不需要它，但以防你需要，它也是可用的。

# 运行 agent

你可以通过 [`Runner`][agents.run.Runner] 类运行 agent。你有 3 个选项：

1. [`Runner.run()`][agents.run.Runner.run]，它以异步方式运行并返回一个 [`RunResult`][agents.result.RunResult]。
2. [`Runner.run_sync()`][agents.run.Runner.run_sync]，它是一个同步方法，底层只是运行 `.run()`。
3. [`Runner.run_streamed()`][agents.run.Runner.run_streamed]，它以异步方式运行并返回一个 [`RunResultStreaming`][agents.result.RunResultStreaming]。它以流式模式调用 LLM，并在收到这些事件时将其流式传输给你。

from agents import Agent, Runner

async def main():
    agent = Agent(name="Assistant", instructions="You are a helpful assistant")

    result = await Runner.run(agent, "Write a haiku about recursion in programming.")
    print(result.final_output)
    # Code within the code,
    # Functions calling themselves,
    # Infinite loop's dance.

## agent 循环

当你在 `Runner` 中使用 run 方法时，你传入一个起始 agent 和输入。输入可以是一个字符串（被视为用户消息），也可以是一个输入项列表，即 OpenAI Responses API 中的项。

然后 runner 运行一个循环：

1. 我们使用当前输入为当前 agent 调用 LLM。
2. LLM 产生其输出。
   1. 如果 LLM 返回 `final_output`，循环结束，我们返回结果。
   2. 如果 LLM 执行交接，我们更新当前 agent 和输入，并重新运行循环。
   3. 如果 LLM 产生工具调用，我们运行这些工具调用，追加结果，并重新运行循环。
3. 如果我们超过传入的 `max_turns`，我们会抛出 [`MaxTurnsExceeded`][agents.exceptions.MaxTurnsExceeded] 异常。

!!! note

判断 LLM 输出是否被视为“最终输出”的规则是：它产生具有所需类型的文本输出，并且没有工具调用。

## 流式传输

流式传输允许你在 LLM 运行时额外接收流式事件。流完成后，[`RunResultStreaming`][agents.result.RunResultStreaming] 将包含有关该运行的完整信息，包括产生的所有新输出。你可以调用 `.stream_events()` 获取流式事件。在[流式传输指南](streaming.md)中了解更多。

## 运行配置

`run_config` 参数让你可以为 agent 运行配置一些全局设置：

- [`model`][agents.run.RunConfig.model]：允许设置要使用的全局 LLM 模型，而不论每个 Agent 拥有什么 `model`。
- [`model_provider`][agents.run.RunConfig.model_provider]：用于查找模型名称的模型提供程序，默认为 OpenAI。
- [`model_settings`][agents.run.RunConfig.model_settings]：覆盖特定于 agent 的设置。例如，你可以设置全局 `temperature` 或 `top_p`。
- [`input_guardrails`][agents.run.RunConfig.input_guardrails]、[`output_guardrails`][agents.run.RunConfig.output_guardrails]：要包含在所有运行中的输入或输出护栏列表。
- [`handoff_input_filter`][agents.run.RunConfig.handoff_input_filter]：要应用于所有交接的全局输入过滤器（如果该交接尚未拥有一个）。输入过滤器允许你编辑发送给新 agent 的输入。有关更多详细信息，请参阅 [`Handoff.input_filter`][agents.handoffs.Handoff.input_filter] 中的文档。
- [`tracing_disabled`][agents.run.RunConfig.tracing_disabled]：允许为整个运行禁用[追踪](tracing.md)。
- [`trace_include_sensitive_data`][agents.run.RunConfig.trace_include_sensitive_data]：配置 trace 是否包含潜在敏感数据，例如 LLM 和工具调用的输入/输出。
- [`workflow_name`][agents.run.RunConfig.workflow_name]、[`trace_id`][agents.run.RunConfig.trace_id]、[`group_id`][agents.run.RunConfig.group_id]：设置该运行的追踪工作流名称、trace ID 和 trace 组 ID。我们建议至少设置 `workflow_name`。组 ID 是一个可选字段，让你可以跨多次运行链接 trace。
- [`trace_metadata`][agents.run.RunConfig.trace_metadata]：要包含在所有 trace 上的元数据。

## 对话/聊天线程

调用任何 run 方法都可能导致一个或多个 agent 运行（因此也可能导致一次或多次 LLM 调用），但它代表聊天对话中的单个逻辑轮次。例如：

1. 用户轮次：用户输入文本
2. Runner 运行：第一个 agent 调用 LLM、运行工具、交接给第二个 agent，第二个 agent 运行更多工具，然后产生输出。

在 agent 运行结束时，你可以选择向用户显示什么。例如，你可以向用户显示 agent 生成的每个新项，或者只显示最终输出。无论哪种方式，用户随后都可能提出后续问题，在这种情况下你可以再次调用 run 方法。

你可以使用基类 [`RunResultBase.to_input_list()`][agents.result.RunResultBase.to_input_list] 方法获取下一轮的输入。

async def main():
    agent = Agent(name="Assistant", instructions="Reply very concisely.")

    with trace(workflow_name="Conversation", group_id=thread_id):
        # First turn
        result = await Runner.run(agent, "What city is the Golden Gate Bridge in?")
        print(result.final_output)
        # San Francisco

        # Second turn
        new_input = result.to_input_list() + [{"role": "user", "content": "What state is it in?"}]
        result = await Runner.run(agent, new_input)
        print(result.final_output)
        # California

异常

SDK 在某些情况下会抛出异常。完整列表在 [agents.exceptions][] 中。概述如下：

- [AgentsException][agents.exceptions.AgentsException] 是 SDK 中抛出的所有异常的基类。
- [MaxTurnsExceeded][agents.exceptions.MaxTurnsExceeded] 在运行超过传递给 run 方法的 max_turns 时抛出。
- [ModelBehaviorError][agents.exceptions.ModelBehaviorError] 在模型产生无效输出时抛出，例如格式错误的 JSON 或使用不存在的工具。
- [UserError][agents.exceptions.UserError] 在你（使用 SDK 编写代码的人）使用 SDK 出错时抛出。
- [InputGuardrailTripwireTriggered][agents.exceptions.InputGuardrailTripwireTriggered]、[OutputGuardrailTripwireTriggered][agents.exceptions.OutputGuardrailTripwireTriggered] 在护栏被触发时抛出。

# 追踪

Agents SDK 包含内置追踪，收集 agent 运行期间事件的全面记录：LLM 生成、工具调用、交接、护栏，甚至发生的自定义事件。使用 [Traces 仪表板](https://platform.openai.com/traces)，你可以在开发和在生产环境中调试、可视化并监控你的工作流。

!!!note

追踪默认启用。有两种方式禁用追踪：

1. 你可以通过设置环境变量 `OPENAI_AGENTS_DISABLE_TRACING=1` 全局禁用追踪
2. 你可以通过将 [`agents.run.RunConfig.tracing_disabled`][] 设置为 `True` 来为单次运行禁用追踪

**_对于使用 OpenAI API 且遵循零数据保留（ZDR）政策的组织，追踪不可用。_**

## Trace 和 span

- **Trace** 代表“工作流”的单个端到端操作。它们由 Span 组成。Trace 具有以下属性：
  - `workflow_name`：这是逻辑工作流或应用。例如“代码生成”或“客户服务”。
  - `trace_id`：trace 的唯一 ID。如果你不传入，则自动生成。必须具有格式 `trace_<32_alphanumeric>`。
  - `group_id`：可选的组 ID，用于链接来自同一对话的多个 trace。例如，你可以使用聊天线程 ID。
  - `disabled`：如果为 True，则不会记录该 trace。
  - `metadata`：trace 的可选元数据。
- **Span** 代表具有开始和结束时间的操作。Span 具有：
  - `started_at` 和 `ended_at` 时间戳。
  - `trace_id`，表示它们所属的 trace
  - `parent_id`，指向此 Span 的父 Span（如果有）
  - `span_data`，即有关该 Span 的信息。例如，`AgentSpanData` 包含有关 Agent 的信息，`GenerationSpanData` 包含有关 LLM 生成的信息，等等。

## 默认追踪

默认情况下，SDK 追踪以下内容：

- 整个 `Runner.{run, run_sync, run_streamed}()` 被包裹在 `trace()` 中。
- 每次 agent 运行时，它被包裹在 `agent_span()` 中
- LLM 生成被包裹在 `generation_span()` 中
- 函数工具调用各自被包裹在 `function_span()` 中
- 护栏被包裹在 `guardrail_span()` 中
- 交接被包裹在 `handoff_span()` 中
- 音频输入（语音转文本）被包裹在 `transcription_span()` 中
- 音频输出（文本转语音）被包裹在 `speech_span()` 中
- 相关音频 span 可能以 `speech_group_span()` 为父级

默认情况下，trace 被命名为“Agent trace”。如果你使用 `trace`，可以设置此名称，或者你可以使用 [`RunConfig`][agents.run.RunConfig] 配置名称和其他属性。

此外，你可以设置[自定义 trace 处理器](#custom-tracing-processors)以将 trace 推送到其他目的地（作为替代或次要目的地）。

## 更高级别的 trace

有时，你可能希望多次调用 `run()` 成为单个 trace 的一部分。你可以通过将整个代码包裹在 `trace()` 中来实现这一点。

from agents import Agent, Runner, trace

async def main():
    agent = Agent(name="Joke generator", instructions="Tell funny jokes.")

    with trace("Joke workflow"): # (1)!
        first_result = await Runner.run(agent, "Tell me a joke")
        second_result = await Runner.run(agent, f"Rate this joke: {first_result.final_output}")
        print(f"Joke: {first_result.final_output}")
        print(f"Rating: {second_result.final_output}")

1. 因为两次对 Runner.run 的调用都被包裹在 with trace() 中，所以各个运行将成为整体 trace 的一部分，而不是创建两个 trace。
   创建 trace
   你可以使用 [trace()][agents.tracing.trace] 函数创建 trace。Trace 需要启动和结束。你有两种方式做到这一点：
1.

推荐：将 trace 用作上下文管理器，即 with trace(...) as my_trace。这将在正确的时间自动启动和结束 trace。

你也可以手动调用 [trace.start()][agents.tracing.Trace.start] 和 [trace.finish()][agents.tracing.Trace.finish]。当前 trace 通过 Python contextvar 进行跟踪。这意味着它会自动与并发一起工作。如果你手动启动/结束 trace，你需要向 start()/finish() 传递 mark_as_current 和 reset_current 以更新当前 trace。

创建 span

你可以使用各种 [\*\_span()][agents.tracing.create] 方法创建 span。一般来说，你不需要手动创建 span。有一个 [custom_span()][agents.tracing.custom_span] 函数可用于跟踪自定义 span 信息。Span 自动成为当前 trace 的一部分，并嵌套在最近的当前 span 下，该 span 通过 Python contextvar 进行跟踪。

敏感数据

某些 span 可能会捕获潜在的敏感数据。generation_span() 存储 LLM 生成的输入/输出，function_span() 存储函数调用的输入/输出。这些可能包含敏感数据，因此你可以通过 [RunConfig.trace_include_sensitive_data][agents.run.RunConfig.trace_include_sensitive_data] 禁用对该数据的捕获。
同样，Audio span 默认包含输入和输出音频的 base64 编码 PCM 数据。你可以通过配置 [VoicePipelineConfig.trace_include_sensitive_audio_data][agents.voice.pipeline_config.VoicePipelineConfig.trace_include_sensitive_audio_data] 禁用对该音频数据的捕获。

自定义追踪处理器

追踪的高层架构是：在初始化时，我们创建一个全局的 [TraceProvider][agents.tracing.setup.TraceProvider]，它负责创建 trace。

我们为 TraceProvider 配置一个 [BatchTraceProcessor][agents.tracing.processors.BatchTraceProcessor]，它批量将 trace/span 发送到 [BackendSpanExporter][agents.tracing.processors.BackendSpanExporter]，后者将 span 和 trace 批量导出到 OpenAI 后端。

要自定义此默认设置，将 trace 发送到替代或额外的后端，或修改导出器行为，你有两个选项：

- [add_trace_processor()][agents.tracing.add_trace_processor] 允许你添加一个额外的 trace 处理器，它会在 trace 和 span 就绪时接收它们。这让你可以在将 trace 发送到 OpenAI 后端之外进行自己的处理。
- [set_trace_processors()][agents.tracing.set_trace_processors] 允许你用你自己的 trace 处理器替换默认处理器。这意味着除非你包含一个执行此操作的 TracingProcessor，否则 trace 将不会发送到 OpenAI 后端。外部追踪处理器列表

# Agent 可视化

Agent 可视化允许你使用 **Graphviz** 生成 agent 及其关系的结构化图形表示。这对于理解 agent、工具和交接在应用程序中如何交互很有用。

## 安装

安装可选的 `viz` 依赖组：

pip install "openai-agents[viz]"

生成图形
你可以使用 draw_graph 函数生成 agent 可视化。此函数创建一个有向图，其中：
*
Agent 表示为黄色方框。

工具表示为绿色椭圆。

* 交接是从一个 agent 到另一个 agent 的有向边。
示例用法
from agents import Agent, function_tool
from agents.extensions.visualization import draw_graph

@function_tool
def get_weather(city: str) -> str:
    return f"The weather in {city} is sunny."

spanish_agent = Agent(
    name="Spanish agent",
    instructions="You only speak Spanish.",
)

english_agent = Agent(
    name="English agent",
    instructions="You only speak English",
)

triage_agent = Agent(
    name="Triage agent",
    instructions="Handoff to the appropriate agent based on the language of the request.",
    handoffs=[spanish_agent, english_agent],
    tools=[get_weather],
)

draw_graph(triage_agent)

这会生成一个图形，直观地表示分诊 agent 的结构及其与子 agent 和工具的连接。
理解可视化

生成的图形包括：

- 一个起始节点（**start**），指示入口点。
- Agent 表示为黄色填充的矩形。
- 工具表示为绿色填充的椭圆。

指示交互的有向边：

- 实线箭头表示 agent 到 agent 的交接。
- 虚线箭头表示工具调用。
- 一个结束节点（**end**），指示执行终止的位置。

显示图形

默认情况下，draw_graph 内联显示图形。要在单独的窗口中显示图形，请编写以下内容：

draw_graph(triage_agent).view()

保存图形
默认情况下，draw_graph 内联显示图形。要将其保存为文件，请指定文件名：

draw_graph(triage_agent, filename="agent_graph")

这将在工作目录中生成 agent_graph.png。
