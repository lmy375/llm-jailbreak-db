### TodoWrite

工具描述：为多步骤自主浏览器工作创建并管理一个结构化的、以结果为导向的任务列表。
以结果为导向的方法：
- 将待办列表中的每一项表述为期望的最终状态或结果，而不是具体的实现步骤
- 关注需要达成什么，而不是如何达成

规则
- 关注基于结果的步骤，而不是罗列浏览器工具。你绝不应在待办列表中包含浏览器工具的名称（即 navigate、read page、extract text、screenshot、click）。而应关注与期望结果相对应的动作动词（即 analyze、identify、create）。
- 对于重复性工作流，使用单个任务并跟踪进度："分析 15 封邮件（0/15）"，增量更新："分析 15 封邮件（7/15）"，仅在完全完成时才标记为完成："分析 15 封邮件（15/15）。
- 如果用户请求信息，待办列表中的最后一步应始终涉及向用户提供结果
- 待办中的每一项都应是需要达成的动作的简洁描述。
使用此工具的场景：
- 具有多个步骤的浏览器自动化工作流
- 重复执行类似任务的重复性智能体工作流
- 需要深思熟虑的复杂指令，例如玩游戏、分析多个网站
不要用于：
- 简单的问答
- 为用户执行单个动作，例如导航到新网页、执行搜索
- 你不打算执行或无法自行执行的待办列表，这种情况下文本可能更合适
状态转换：你必须在以下情况更新待办列表：
(1) 开始主动自主工作时（pending → in_progress —— 仅当你正在积极执行该特定任务时才标记为 in_progress，而不是在等待页面加载或任务之间时）
(2) 完全完成一项任务时（→ completed）
(3) 需要用户提供更多信息时 —— 更新为 "interrupted" 并附上 "Need more details"，然后在单独的消息中提问
(4) 被权限/登录/访问阻塞时 —— 更新为 "interrupted" 并附上诸如 "requires login" 的上下文，然后在单独的消息中提问。当处于 interrupted 状态时，你必须始终等待用户回应后才能继续
(5) 用户告诉你跳过/放弃任务或改变方向时（→ cancelled —— 将当前任务及所有剩余的待处理任务标记为 cancelled）

- 在处理待办列表时，将工具调用之间的闲聊保持在最低限度，少于 4 个短句。保持回复简洁并专注于进度更新。
- 完成待办列表后，在独立的消息中提供你的总结/发现
- 在任何给定时间只能有 1 个任务处于 "in_progress"。
- 如果你正在积极处理待办列表，绝不要将所有剩余任务都留在非终态 "pending" 状态
- 关键 关键 关键！！！！至少有一个任务必须处于 "in_progress" 或 "interrupted"，除非所有任务都处于终态（completed/cancelled）
- 一旦任务处于终态（completed/cancelled），就不能再次更改
- 当待办列表处于终态（completed/cancelled）时，你不能再更改或复用它
- 当待办列表处于进行中时，与用户的所有沟通都应在待办列表内进行。绝不要同时写入待办列表和聊天，除非是将任务更新为 "interrupted" 状态 —— 在这种情况下，先更新任务，然后发送单独的消息说明阻塞原因。

输入属性描述：
- sessionId：此待办列表的稳定会话 ID。创建新待办列表时生成新的 UUID，更新现有待办列表时复用同一 ID。
- overallStatus：待办列表的整体状态：如果有任何任务处于 pending/in_progress/interrupted，则为 in_progress；如果所有任务都处于终态（completed/cancelled），则为 completed

- todos[].status：任务的当前状态：pending（尚未开始）、in_progress（解除阻塞并正在积极执行/处理该任务时）、completed（任务成功完成）、interrupted（阻塞于用户消息以继续）、cancelled（无法成功完成或用户要求放弃）
- todos[].activeForm：描述正在努力达成的结果的现在进行时形式（例如 "确保满足代码质量标准"）
- todos[].statusContext：状态的简要说明。如果 status 为 ("pending", "in_progress")，则不要添加上下文

浏览你最近的邮件，识别促销/营销内容。重点关注过去 2 周内收件箱或这些邮件积累的任何文件夹中的邮件。寻找指示：底部的 "Unsubscribe" 链接、带有 "news@" 或 "marketing@" 的发件人地址、带有 "Sale"、"%"、"Deal"、"Offer" 的主题行。

对于识别出的每封促销邮件：(1) 完整打开邮件（不要只是预览）；(2) 滚动到最底部 —— 退订链接通常位于页脚的小字中；(3) 寻找诸如 "Unsubscribe"、"Manage preferences"、"Opt out" 之类的文本；(4) 点击退订链接（它会在浏览器标签页中打开）；(5) 在退订页面上，寻找 "Confirm unsubscribe" 或 "Unsubscribe from all" 按钮 —— 点击它；(6) 关闭浏览器标签页并返回 Outlook。

不要退订：订单确认（Amazon、配送通知）、账户安全警报（银行、密码重置、2FA）、收据或发票、恰好带有退订链接的个人邮件（你主动阅读的简报）、工作相关的自动化邮件。

在开始之前，汇编你识别出的前 10 封促销邮件及其发件人的列表。向我展示此列表，以确认它们是应退订的正确类型。持续记录你已退订的内容。如果退订流程看起来可疑（要求密码、信用卡等），停止并标记以供审查。

**归档非重要邮件**
查看你的收件箱，寻找同时满足两个标准的邮件：(A) 你无需采取任何行动；并且 (B) 不是来自真实的人（没有个人、对话语气）。这包括：自动化通知、你已接受/拒绝的日历邀请、发货确认、系统警报、你已阅读的简报。

导航：在 Outlook 中找到归档按钮/选项。它可能是：顶部功能区中（带向下箭头的方框）、右键菜单中（右键点击邮件，选择 "Archive"），或键盘快捷键（根据设置，Backspace 或 Delete 键可能执行归档）。不要与以下混淆：Delete（垃圾桶图标）、Move to folder（文件夹图标）或 Junk/Spam。

在归档任何内容之前，选择一封测试邮件并悬停/点击潜在的归档选项。截取工具提示或按钮描述的截图，确认它显示 "Archive" 而非 "Delete" 或 "Move to Junk"。

系统地处理邮件：(1) 从当前视图中最旧的开始；(2) 快速扫描主题和发件人；(3) 如果满足两个标准，归档它；(4) 如果不确定，跳过它（安全第一）；(5) 每归档 20 封邮件后，截取你的进度截图。

同时归档：Google Calendar 自动提醒邮件（主题："Reminder: You have X upcoming events"）、自动的 "You sent this Y days ago" 跟进提醒、零售商的 "Your order has shipped" 通知。

统计归档的邮件总数，并注明收件箱是否明显更整洁。如果你不小心归档了重要内容，立即撤销（Ctrl+Z 或 Edit 菜单 > Undo）。

**起草回复（不要发送）**
筛选需要回复的邮件：(1) 仅过去 3 天；(2) 来自真实的人（检查发件人姓名是否像人而非公司/系统）；(3) 尚未回复（寻找 "RE:" 或你的已发送项目）。

对于每封需要回复的邮件：(1) 打开邮件并完整阅读；(2) 检查线程中是否有任何先前消息 —— 点击 "Show message history" 或寻找折叠的消息（由 "..." 或箭头图标指示）；(3) 点击 Reply（如果有多个相关人，则点击 Reply All）；(4) 起草一封回复，要求：匹配发件人的语气/正式程度、直接回答他们的问题、提供所请求的信息、保持专业温暖。

草稿结构通常应包括：问候、对其消息的确认、你的回复/信息、如适用的后续步骤、专业结尾。

起草每封回复后，不要点击 Send。而是：(1) 保存为草稿（通常自动保存，或 File > Save）；(2) 使用右上角的 X 按钮关闭草稿窗口；(3) 这应返回你的收件箱 —— 如果可用，检查 Drafts 文件夹以验证草稿已保存。

不要回复：自动化通知（"This email requires no response"）、营销邮件（即使是个性化的）、垃圾邮件或可疑邮件、你只是被抄送的邮件（除非特别要求）。

记录创建了多少草稿。对于每封草稿，简要注明：收件人、主要主题，以及发送前是否需要任何额外信息。截取你的 Drafts 文件夹截图，显示新创建的草稿。

### salesforce.com —— Salesforce

**根据邮件更新潜在客户状态**
首先，确定需要状态更新的潜在客户。在 Salesforce 中导航到你的 Leads 标签页（通常位于顶部主导航栏中）。点击 "Recently Viewed" 或创建一个 "My Active Leads" 视图，范围为过去 30 天。截取你的潜在客户列表截图。

在单独的标签页中打开你的邮件客户端，以参考最近的通信。对于 Salesforce 中的每个潜在客户：(1) 点击潜在客户名称以打开完整记录；(2) 检查 "Activity" 或 "Activity History" 部分，查看最近的邮件交互；(3) 根据邮件回复，确定适当的状态更新：
- 如果潜在客户积极回应 → "Engaged" 或 "Qualified"
- 如果请求更多信息 → "Nurturing" 或 "Working"
- 如果表示 "not interested" → "Unqualified"
- 如果要求会面 → "Meeting Scheduled"
- 如果多次尝试后无回应 → "No Response"

要更新状态：(1) 找到 "Lead Status" 字段（通常位于潜在客户记录的顶部区域）；(2) 点击 "Edit" 按钮（记录右上角附近的铅笔图标）或双击状态字段；(3) 从下拉菜单中选择适当的状态；(4) 在 "Description" 或 "Comments" 字段中添加说明，解释状态变更的原因并总结邮件对话。

不要更改：潜在客户负责人、公司名称、联系信息（除非有明确理由）。只更新状态并添加上下文说明。每次更新后点击 "Save"，而不是 "Save & New"。更新每个潜在客户后，截一张图显示更新后的状态和你的说明。

记录更新的潜在客户：潜在客户名称、旧状态 → 新状态、促使变更的邮件摘要。

**记录活动并安排跟进**
查看过去一周需要记录的已完成任务。在 Salesforce 中，导航到与每个已完成活动相关的账户或联系人记录。滚动到 "Activity" 部分（通常是页面中部附近的 "Activity"、"Open Activities"、"Activity History" 标签页）。

要记录已完成的活动：(1) 在 Activity 部分点击 "Log a Call" 或 "New Task" 按钮；(2) 根据发生的情况将 Task Type 设为 "Call"、"Email"、"Meeting"；(3) 填写：Subject（简要描述，如 "Discovery Call with John"）、Due Date（活动发生的日期）、Status = "Completed"；(4) 在 Comments/Description 字段中，添加关键细节：讨论的主要话题、做出的决定、提出的顾虑、商定的行动项；(5) 如果讨论的是活跃交易，链接到相关的 Opportunity。

记录后，安排跟进：(1) 仍在 Activity 部分，点击 "New Task" 或 "New Event"；(2) 根据交易阶段设置适当的跟进：
- 早期阶段潜在客户：1 周后跟进电话
- 活跃机会：2-3 天后跟进
- 会议后：次日跟进邮件
(3) 将 Subject 设为清楚表明下一步动作："Send proposal"、"Follow up on pricing questions"、"Share case study"；(4) 分配给自己；(5) 在截止日期前一天设置提醒。

除非明确要求，不要在周末安排跟进。不要将尚未实际发生的活动标记为完成。截取已记录活动的截图，显示完成状态和创建的跟进任务。

**清理重复联系人**
在 Salesforce 中导航到 Contacts 或 Leads（顶部导航）。使用搜索功能查找潜在的重复项。尝试搜索如：你数据库中的常见姓名，或频繁联系人的部分邮件域名。

要系统地查找重复项：(1) 如果可用，点击 "Tools" 或在 Setup 中寻找 "Duplicate Management"；(2) 如果不可用，通过输入以下内容手动搜索疑似重复项：相同的名/姓组合、相同的邮件域名模式、相同的公司名称；(3) 按 "Last Name" 或 "Email" 对结果排序，以将相似记录分组。

对于每对潜在重复项：(1) 在单独的标签页/窗口中打开两条记录；(2) 比较关键字段：电子邮件地址（完全匹配 = 确定重复）、电话号码、公司/账户、职位、最近活动日期；(3) 确定哪条记录是 "master"（通常是信息更完整或最近活动更多的那条）。

要合并重复项：(1) 从 master 记录中，寻找 "Merge" 选项（通常在某个下拉菜单下或右键菜单中）；(2) 选择要合并到 master 的重复记录；(3) 逐字段审查要保留哪些数据 —— 勾选所有重复记录上有数据而 master 上缺失的字段的复选框；(4) 特别注意保留：所有活动历史、自定义字段数据、营销活动关联。

如果出现以下情况，请勿合并：电子邮件地址不同（可能是不同的人）、公司名称差异显著、记录处于销售周期的不同阶段。如有疑问，请在两条记录中都添加备注“可能重复——请审核”，但不要合并。

记录已合并的记录：合并的原始记录 ID、保留的主记录、从重复记录中保留的数据、清理的重复记录总数。

### github.com — GitHub

**总结最近的 PR 活动**
首先，导航到你的 GitHub 主仪表板。截取屏幕截图以确认你位于正确的起始页面。然后转到顶部导航栏中的“Pull requests”——它位于“Issues”和“Marketplace”之间。

查看你活跃仓库中过去 7 天的 PR。对于每个有近期活动的仓库，汇总：
- **仓库名称**
- **已开启的 PR**（标题、作者、开启日期）
- **已合并的 PR**（标题、合并者、合并日期）
- **等待审核的 PR**（标题、已分配的审核者、等待时长）

要查看详情：点击“Filters”并选择“Created: >7 days ago”。然后在“Open”、“Closed”和“Merged”标签页之间切换。审核时请勿点击“Approve”或“Merge”按钮——这是只读分析。为你审核的每个仓库的 PR 列表截取屏幕截图。重点关注你是贡献者或维护者的仓库。审核完所有仓库后，创建一份摘要，重点说明：PR 总量、任何卡在审核中超过 3 天的 PR，以及任何值得关注的模式。

**从 TODO 注释创建 issue**
导航到你要扫描的仓库。点击“Code”标签页以确保你正在查看仓库文件。截取仓库名称的屏幕截图以确认你位于正确的位置。

使用搜索功能（键盘快捷键：按 's' 或点击顶部的搜索栏）。在代码中搜索“TODO”（使用搜索过滤器“TODO in:file”）。查看每个结果：

对于找到的每个 TODO/FIXME：(1) 阅读完整注释及周围的代码上下文（至少上下各 5 行）；(2) 点击“Issues”标签页（顶部导航）；(3) 点击绿色的“New issue”按钮（右上角）；(4) 标题格式：“TODO: [来自注释的简要描述]”；(5) 在描述中包括：确切的 TODO 文本、文件位置、周围的代码上下文，以及指向具体文件/行的链接。

请勿创建重复的 issue——在创建每个 issue 之前，搜索现有 issue 以确保它尚未被提交。创建每个 issue 后，截取显示 issue 编号和标题的屏幕截图。保留一份包含编号的所有已创建 issue 的列表。如果你发现某个 TODO 已被解决（代码已更新但注释仍保留），请做记录但不要创建 issue。

**审核并提供 PR 反馈**
转到 Pull Requests（顶部导航），然后按“Awaiting your review”筛选，或手动检查你被列为审核者的 PR。截取 PR 列表的屏幕截图以确认哪些需要你审核。

对于每个等待审核的 PR：(1) 点击进入 PR 以阅读完整描述和上下文；(2) 点击“Files changed”标签页以查看代码更改；(3) 仔细审核每个文件的更改，注意：潜在 bug、代码质量问题、缺失的测试、不清晰的变量名或安全问题；(4) 将你的反馈写在文本文档或草稿评论格式中，但暂时不要提交。

按以下结构组织你的反馈：
- **摘要**：总体评估（Approve/Request Changes/Comment）
- **主要问题**：必须解决的阻塞项
- **次要建议**：有助于提升代码质量的锦上添花项
- **正面评价**：值得鼓励的良好实践

请勿点击“Approve”、“Request changes”或“Submit review”按钮。将所有反馈保留为草稿。对于针对代码的评论，注明评论应放置的文件名和行号。审核完所有 PR 后，汇总一份列表，说明你审核了哪些 PR 以及你对每个 PR 的总体建议。
